# Background delegate results: delivery timing and duplicate consumption

## Question and short answer

How do coding agents deliver a background subagent/task result to a busy parent, prevent polling and notification from delivering it twice, and constrain interim messages?

**Recommendation for pi-squire: use `steer` for completed results, keep the existing reply-ID deduplication, and make status guidance explicitly say that completion results are delivered automatically and need not be polled or independently read.** This is the smallest change that closes the observed “result is known, but its notification waits until after the answer” window. It is not an exactly-once guarantee: if both polling and push are intended to return result content, they need a shared consumption/ownership mechanism, not merely a different queue. The strongest precedents are edxeth/pi-subagents' wait-versus-notification ownership, Codex's mailbox-only wait, and Cursor's advice to consume only one of its overlapping stream representations. Claude Code has an issue reproducing almost exactly the pi-squire failure, so its notification design is a cautionary example, not evidence that the problem is solved. [P1–P3, E1–E3, C1–C4, U1–U2, A1–A3]

## The relevant implementation patterns

### 1. Queue acceptance is not parent consumption

pi-squire's `takeReply` marks the reply ID shown, queues the custom message, persists a result record and updates status. A parent can therefore see a terminal result and its path before seeing the queued report. The shown set solves **transport duplicates** (the same mail envelope arriving again), not **semantic duplicates** (the same report obtained through a tool/file and later through the message queue). Its existing tests explicitly check one reply is shown once, including after resume; they do not establish cross-channel consumption. [P1–P2]

Claude Code issue #33872 reports the same distinction: an enqueue/notified flag can prevent multiple pushes but cannot erase a push already queued before `TaskOutput` returns content. The report's proposed fix is queue withdrawal or giving an active blocking reader sole delivery ownership. This is an upstream user report, not a verified description of proprietary current implementation; a commenter also reports structured-output failure after the late turn. [A2–A3]

### 2. Use one content delivery channel; let waiting be notification-aware

Codex v2 separates “wait until input exists” from “return a child result.” `wait_agent` subscribes to input-queue activity, observes preexisting activity without a lost-wakeup race, and returns an outcome. The completion content remains in the mailbox to be included in model input. This avoids creating a second content-bearing wait result. Tests separately specify that queued mail does not reopen an already-finalized answer. [C1–C4]

edxeth/pi-subagents instead permits both content-bearing wait and content-bearing notification, but chooses an owner **before completion**: wait sets `resultOwner`, `allowSteerDelivery = false`, and `deliveryState = "awaited"`; completion routing honors that claim. Timeout releases ownership and restores detached delivery. Its cached-result path intentionally permits retrieval again, so adopting its pattern should not be described as exact-once across every read. [E2–E3]

Cursor's current stream docs provide a closely related client-side warning: simplified text/tool events and richer `interaction_update` events overlap, so select one representation and ignore the other. Polling a run and also consuming its terminal SSE event likewise requires client-side ownership; the docs do not promise that a GET consumes the event. [U1]

### 3. Safe injection is a boundary, not necessarily an interruption

In the installed Pi loop, the tool batch is awaited and its results recorded before the steering queue is fetched. Follow-up is fetched only after the inner tool/steering loop would stop. Switching result delivery to steer therefore does **not** abort the ongoing Bash/read tool call; it brings the report to the next model request. A report arriving after an assistant's no-tool final message can still provoke continuation: steer cannot promise the parent has not already spoken. [P3–P4]

Avoid importing current Codex's more aggressive scheduling into Pi by analogy. Its tests permit mailbox mail to drive continuation after reasoning/commentary response items and specifically distinguish final answers; Pi's API names describe a different boundary. [C2, P4]

### 4. Do not treat completion as new authorization

Claude's current docs say subagent output is under a header that marks its instructions and approval claims as the subagent's words, not user authority; background completion is an automated event, not a user message. nicobailon's completion action likewise explicitly forbids inferring authorization or rerunning completed work, and holds resumption after user stop. These are useful safeguards independent of queue choice. [A1, N1–N2]

Historical Codex issue #14318 reports late results entering a newer unrelated task because delivery lacked originating-turn binding (reported source `2cfa106`, March 11, 2026). Current completion source carries agent paths and originating turn metadata for completion activity, but this research does **not** establish that every scenario in that issue is fixed. Correlation should identify delegation, original task, and result status, rather than say simply “done.” [C1, C5]

## Recommendation for pi-squire

1. **Prefer `steer` to `followUp` for terminal result messages.** In the observed case, the delegate's result is relevant to the run currently collecting it, not a separate request to perform after that run. Pi's batch boundary is the desired point. This recommendation rests on installed Pi source and edxeth's default detached-result route, not a claim that every product chooses steer. [P1, P3–P4, E2]
2. **Retain transport dedupe by reply ID.** Changing queues does not replace the shown-set protection or its resume behavior. [P1–P2]
3. **Prefer clear status guidance over hiding the result path.** Say that terminal reports are automatically delivered into this conversation, no polling is needed to obtain them, and a done status means the result has arrived at the extension—not necessarily that its queued message has been read by the model. Keeping paths preserves diagnostics; hiding them is not an acknowledgment protocol and cannot stop ordinary filesystem inspection. This is a design judgment based on the two existing channels in pi-squire. [P1–P2]
4. **If the requirement is strict suppression after result retrieval, add an explicit result-consumption seam shared with notification delivery.** For example, a result-reading tool claims delivery ownership before returning content, and the notification path skips an owned result or withdraws its queued notice. Do not mark a mere status check as consumption: it does not provide the report and could silently lose useful results. An arbitrary built-in `read` or Bash command reading a file cannot safely be inferred from “status returned a path.” These are proposed designs, not existing behavior; edxeth's wait owner and Codex's notification-only wait provide evidence for the underlying pattern. [E2–E3, C3–C4]
5. **Keep the already-decided final-only findings rule.** The reviewed systems often structurally separate internal/UI progress from the final parent result, but Google ADK explicitly permits intermediate updates, and no cross-framework universal ban was found. For pi-squire, final-only findings are appropriate to its report-only task contract; questions/blockers can be a separately defined escalation rather than repeated report content. [E1, O1, S1, G1]

A minimal validation matrix for a future change: result arrives during a long tool call; result arrives while `delegation_status` runs; result arrives after an assistant final answer; multiple results arrive together; an envelope replays after resume; and user abort occurs before completion. These are proposed tests, **not tests executed by this research**. Steer addresses timeliness, while a claimed content-delivery channel addresses semantic deduplication; test the two separately.

## Model reaction risks and unknowns

- **No controlled evidence was found that GPT-family models generally react worse than Claude to Pi-style tool-boundary result injection.** That model-specific claim remains **unknown**. The task context's GPT interim-mail behavior was not benchmarked here.
- **There is evidence of scheduling/correlation failures, not a proven general defect in mid-run model reasoning:** Claude #33872 reports repetitive turns, unauthorized continuation risk, and a commenter reports structured-output failure; Codex #14318 reports newer-task contamination. Both are historical user reports in upstream trackers, not vendor guarantees or controlled cross-model studies. [A2–A3, C5]
- Claude Code's exact current task-notification queue internals and strict read-versus-notification dedupe remain **unknown**. Current official docs establish later-turn background subagent completion, not every `TaskOutput`/old `BashOutput` version's implementation. [A1–A3]
- Cursor's internal LLM-parent subagent injection timing is **unknown**. Its public Cloud Agents API documents external client polling/streaming, which should not be conflated with the foreground Agent's scheduler. [U1–U2]
- Automatic duplicate final `FunctionResponse` suppression in Google ADK is **unknown**. Correlation IDs and resumability alone do not prove exactly-once delivery. [G1–G2]
- No live provider sessions, executable upstream test suites, or pi-squire behavior changes were attempted. Only this research file was added to the repository, uncommitted.
