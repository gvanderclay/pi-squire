# Parent delegation context APIs

## Question and short answer

What is the best supported way for pi-squire to expose dynamic per-agent selection descriptions and optional user-authored parent delegation guidance, without choosing an autonomy policy for the user?

Keep agent selection descriptions in the `delegate` tool declaration and keep optional parent guidance attached to that tool. Refresh changed content at `before_agent_start`, not only `session_start`, if “dynamic” means edits become visible on the next run. The proposed `<agent dir>/delegation.md` → `promptGuidelines` design is supported at the advertised Pi 0.80.5 floor, but **re-registering inside `before_agent_start` alone leaves the current run's prompt-guideline snapshot stale on Pi 1.0.0 and 1.3.0**. Re-register changed tool metadata and synchronize that run's structured `toolGuidelines.delegate` from the same snapshot on those versions; do not replace the whole system prompt. If the project elects to raise its minimum, a dedicated structured prompt section is a cleaner surface for an arbitrary Markdown document, but it still needs explicit active-tool gating and does not replace the roster's tool description. [C01–C16, C22–C25]

This is a mechanism recommendation, not a proposed instruction to delegate more or less. An absent file should add no parent-policy text. Leave operational facts (fresh child, self-contained task, asynchronous result delivery) in the package; let the user write authorization, preferences, and selection policy. [C01–C04, C17, C18]

## API comparison

**C06. `description` is the tool declaration's model-facing capability text.** It is required in `ToolDefinition`, alongside parameters and execution; `promptSnippet` and `promptGuidelines` are optional additions. Thus the roster belongs in `description` even if a separate system-prompt section exists. Evidence: `P13:dist/core/extensions/types.d.ts:451–465`; `P13:docs/extensions.md:133–143`; P80 has the same optional fields in `dist/core/extensions/types.d.ts:333–345`.

**C07. `promptSnippet` is a one-line tool-list summary, not a Markdown-document slot.** The type calls it an optional snippet for the system prompt tool list. Pi normalizes it by collapsing whitespace; absent snippets are omitted from that list. It does not replace the tool's actual description. Evidence: `P13:dist/core/extensions/types.d.ts:459–463`; `P13:dist/core/agent-session.js:1250–1257,1272–1281`; `P13:dist/core/system-prompt.js:84–87`. A short operational summary could be added, but not the entire roster or `delegation.md`.

**C08. `promptGuidelines` is tool-scoped instruction text.** Pi normalizes/trim-deduplicates string entries and emits them as rule bullets for declared tools, followed by global `promptGuidelines`. One arbitrary multiline Markdown file passed as one entry therefore becomes one bullet whose following lines retain their internal Markdown; it is not parsed into Markdown sections or semantic individual rules. Evidence: `P13:dist/core/agent-session.js:1259–1270,2877–2883`; `P13:dist/core/system-prompt.js:31–65`. Use the whole trimmed file as one entry if retaining the proposed format; do not invent a Markdown-to-bullets parser.

**C09. Gating comes with tool-scoped guidelines, but not with arbitrary global instructions.** P13 builds rules from selected tools minus `hiddenTools`; inactive or hidden declarations do not contribute those rules. A custom section or global `promptGuidelines` entry is not automatically tied to `delegate`. P80 instead gathers registered-tool guidelines only for valid active names when rebuilding the base prompt. Evidence: `P13:dist/core/system-prompt.js:56–65,76–87`; `P13:docs/extensions.md:159–186`; `P80:dist/core/agent-session.js:694–725`. Do not reactivate a disabled delegate tool merely to expose guidance.

**C10. Re-registration replaces this extension's same-name tool and triggers a runtime refresh.** `registerTool()` calls `extension.tools.set(tool.name, ...)` then `runtime.refreshTools()`. Refresh reconstructs definitions, executable wrappers, prompt snippets, and guidelines. Existing direct tools keep their prior active state unless the allowed-tool configuration or exposure transition requires otherwise. Evidence: `P13:dist/core/extensions/loader.js:231–243`; `P13:dist/core/agent-session.js:2839–2923`; P80 replacement/refresh in `dist/core/extensions/loader.js:184–190` and active-name retention in `dist/core/agent-session.js:1911–1992`. A tool description is fixed in its registered definition, not immutable for the entire session.

**C11. Session-start is not the only supported dynamic-registration boundary.** The official `dynamic-tools.ts` example registers during `session_start` and later from `/add-echo-tool`; the factory's registration hook is available before core runtime binding, while action methods such as tool enumeration throw then. This explains the current initial-unvalidated roster and the second session-start registration, but does not require waiting until the next session to refresh descriptions. Evidence: `P13:examples/extensions/dynamic-tools.ts:1–75`; `P13:dist/core/extensions/loader.js:106–130`; `S:src/index.ts:388–399,622–626`.

**C12. On P13, `before_agent_start` is per new run, not per tool-loop model request.** `_prepareRun()` checks compaction, emits the event, constructs initial messages, and applies the resulting prompt/loadout; subsequent low-level continuation stays within the run. Idle custom-message starts and user starts both call this preparation in P13. Evidence: `P13:dist/core/agent-session.js:1390–1500,1815–1842`; `P13:docs/extensions.md:62–69,104`. Refreshing here gives “next run” freshness, not live filesystem watching during one long run.

**C13. Structured options are mutable and compositional on P13.** The runner clones/normalizes baseline options, passes one mutable current-options object through handlers in order, rerenders `event.systemPrompt`, and returns those options. The official prompt-customizer modifies `event.systemPromptOptions.sections.tool_guidance` and deletes it when absent. Exported options include `selectedTools`, `hiddenTools`, `toolSnippets`, `toolGuidelines`, `promptGuidelines`, and `sections`. Evidence: `P13:dist/core/extensions/runner.js:1121–1163`; `P13:dist/core/system-prompt.d.ts:5–48`; `P13:examples/extensions/prompt-customizer.ts:39–48`; `P13:dist/index.d.ts:8` exports the public types.

**C14. Whole-string replacement is not the recommended structured-update path.** Returning `{systemPrompt: ...}` sets `forceSystemPrompt`; Pi still diffs/persists structured sections but projects the forced string into the leading system message of provider requests instead. This creates different recorded versus forced prompt representations, and replacing with a freshly constructed string risks dropping other instructions. Evidence: `P13:dist/core/extensions/runner.js:1147–1153`; `P13:dist/core/agent-session.js:1299–1363`; `P13:docs/extensions.md:104`. Preserve unrelated sections and other extensions' changes.

**C15. Important refresh trap: re-registration inside the event updates the baseline, not its already-cloned current-run guideline map.** The runner clones options *before* executing handlers; tool refresh then replaces `_baseSystemPromptOptions`. `_prepareRun()` reconciles active tool names but uses the event result's existing `toolGuidelines` and snippets for its prompt. Tool definitions and prompt-guideline text can therefore disagree for that run unless synchronized. Evidence: `P13:dist/core/extensions/runner.js:1121–1123`; `P13:dist/core/agent-session.js:1272–1297,1456–1465,1494–1495,2839–2923`. P10 uses the same cloned-options architecture (`dist/core/extensions/runner.js:1115` onward and `dist/core/agent-session.js:1555–1591`).

**C16. An assert-based probe confirmed the snapshot behavior on both installed versions.** Command `node /tmp/squire-context-api-research/probe.mjs` called the real `ExtensionRunner.prototype.emitBeforeAgentStart` with a fake extension, changed baseline `toolGuidelines.delegate` during the handler, and added a structured section. Output:

```text
1.3.0: before_agent_start clones base options; changing registration/base during handler does not update current-run toolGuidelines; structured section edit survives
1.0.0: before_agent_start clones base options; changing registration/base during handler does not update current-run toolGuidelines; structured section edit survives
```

The assertions checked that the event result retained `['old']` tool guidelines but contained the new section. This probes the actual runner's copying behavior, not a complete live registration/model request or provider integration.

**C17. `context`/`context_with_system` are request-time transformations, not durable configuration setters.** The runner structured-clones messages; ordinary `context` sees only conversation and has system state restored. Then `context_with_system` sees the full transcript and its result is honored, with an error if it removes the leading system message. They are appropriate for deliberate request projections, not necessary for this tool-owned parent guidance. Evidence: `P13:dist/core/extensions/runner.js:1001–1062`; `P13:docs/extensions.md:114–116`. Request-local injection would also need to be rebuilt on each relevant request rather than relying on a persisted prompt change.

**C18. `sendMessage` and `sendUserMessage` add conversation, not tool-attached policy.** Custom messages persist as `custom_message` entries; `display: false` hides rendering, not model context, and custom content converts to user-role text. `sendUserMessage()` always triggers or queues a turn and enters through prompt processing as extension input. `sendMessage()` can trigger an idle run, queue steering/follow-up, defer to nextTurn, or append without triggering. Evidence: `P13:dist/core/agent-session.js:1803–1907`; `P13:docs/message-types.md:229–243`; `P13:docs/session-format.md:202–219`. Injecting the same parent policy as a hidden message on every prompt unnecessarily creates history entries and makes old versions summarizable conversation content.

**C19. A `before_agent_start` returned `message` also becomes conversation history.** `_prepareRun()` turns each handler message into a custom message and appends it beside the starting input; it is distinct from mutating prompt options. Evidence: `P13:dist/core/agent-session.js:1482–1495`; `P13:dist/core/extensions/types.d.ts:1125–1129`. Do not use that return slot for recurring parent guidance.

## Caching, transcript, compaction, and child delivery

**C20. Structured changes are transcript deltas, not inherently cache destruction.** P13 computes named section diffs; unchanged sections produce no patch. Initial prompt/tool state and later section/tool changes are persisted. Unsupported provider transitions can require a complete checkpoint and invalidate the prefix cache. Evidence: `P13:dist/core/system-prompt.js:143–157`; `P13:dist/core/agent-session.js:1308–1313`; `P13:docs/extensions.md:184–188`; `P13:docs/session-format.md:87–98`. Refresh from stable file contents; avoid timestamps or gratuitous wording churn. No claim of identical cache behavior across providers follows.

**C21. Compaction preserves structured system state separately from the prose summary.** P13 compaction stores the replayed prompt/tool checkpoint in `CompactionEntry.systemMessage`; reconstruction makes it the leading system message and drops superseded kept system deltas. Conversation custom messages instead participate in normal retained/summary history. Evidence: `P13:docs/session-format.md:133–152,249–265`; `P13:dist/core/session-manager.js:882–895`; `P13:docs/compaction.md:43–49,147–155`. Tool guidance is not dependent on a summarizer remembering the exact policy wording. This P13 checkpoint statement must not be projected backward onto P80.

**C22. The child first-turn workaround remains relevant to the advertised floor.** `src/child.ts` claims the parent's inbound request and sends it via `pi.sendUserMessage(..., {deliverAs:'steer'})`, ensuring a user-prompt startup path. `src/results.ts` delivers completed reports to the parent with a custom `sendMessage(..., {triggerTurn:true, deliverAs:'steer'})`. P13's changelog records that idle custom-message runs gained `before_agent_start` handling in **1.2.0**, fixing issues including #5581; therefore 1.0.0 and the advertised older floor cannot be assumed to run a new parent-refresh handler on a custom-result wake. Evidence: `S:src/child.ts:15–20,69–86`; `S:src/results.ts:327–350`; `P13:CHANGELOG.md:49–62,87`; `P13:dist/core/agent-session.js:1836–1842`. Keep session-start registration for initial/resume state and keep the child workaround while older Pi remains supported.

## Compatibility-floor findings

**C23. P80 supports tool metadata and dynamic re-registration but structured options are inspection-only in the observed execution path.** P80 exposes `systemPromptOptions: BuildSystemPromptOptions`, `promptSnippet`, and `promptGuidelines`; however its runner only consumes a handler's returned `message` or `systemPrompt`, and prompt processing then installs the returned string or `_baseSystemPrompt`. It does not render mutations to event options. Mere presence of the property in exported types is not evidence of today's mutation semantics. Evidence: `P80:dist/core/extensions/types.d.ts:333–345,517–524`; `P80:dist/core/extensions/runner.js:784–834`; `P80:dist/core/agent-session.js:864–896`.

**C24. Tool-scoped guideline refresh can use P80's existing baseline rebuild rather than whole-prompt replacement.** P80 re-registration refreshes the registry, calls `setActiveToolsByName`, rebuilds `_baseSystemPrompt` including active tools' guidelines, and normal prompt processing resets to that updated base after the event. Thus the old-version path can remain tool metadata driven; it cannot use a modern named section directly. Evidence: `P80:dist/core/agent-session.js:617–633,694–725,880–896,1911–1992`; `P80:dist/core/extensions/loader.js:184–190`. This is source-verified API behavior, not a live end-to-end pi-squire-on-0.80.5 test.

**C25. Modern mutation and custom-start support have different floors.** P10 already supports mutable structured options and `context_with_system` in exported types; its runner returns the normalized changed options. P13 additionally handles both user and custom run triggers. Transcript-backed section changes were introduced in Pi 0.86.0 according to the first-party changelog, while custom-start parity arrived in 1.2.0. Evidence: `P10:dist/core/extensions/types.d.ts:661,699–702,1158`; `P10:dist/core/extensions/runner.js:1115` onward; `P13:CHANGELOG.md:535–553,49–62`. Prefer a tested version boundary over assuming all versions between P80 and P10 behave identically.

## Recommended seams and corrections to the proposal

**C26. Parent registration seam.** The existing `delegateTool()` factory and `session_start` registration in `src/index.ts` are the narrow places to build tool metadata; the early child return keeps parent-only behavior separate. `src/agents.ts` owns roster parsing, not parent guidance policy. Evidence: `S:src/index.ts:369–373,399,545–548,622–626,683`; `S:AGENTS.md:8–17`. Recommendation: take one roster/guidance snapshot per refresh and derive the definition and current-run prompt data from that same snapshot, rather than making two filesystem reads that can disagree.

**C27. File contract seam.** The existing convention resolves agent data through `getAgentDir()` and the README defines that root rather than a project-only `.pi` path. Evidence: `S:src/index.ts:399`; `S:README.md:46–49`. Recommendation: read exactly `join(getAgentDir(), 'delegation.md')` in the parent branch, treat missing/empty content as no guidance, report non-missing read failures without preventing delegation, and replace/remove old guidance on edits/deletion. Add no default autonomy paragraph, no second project discovery hierarchy, and no propagation into child role files.

**C28. Exact choice at `before_agent_start`: use both APIs for different owners, not either indiscriminately.** Re-registration owns the model-facing tool `description`; event `systemPromptOptions` owns the current run's structured prompt. The former cannot be replaced with `sections` if the tool schema is to remain current, and the latter needs synchronization because of C15. Evidence: `P13:dist/core/extensions/loader.js:231–243`; `P13:dist/core/extensions/runner.js:1121–1163`; `P13:dist/core/agent-session.js:1456–1495`. Recommendation with the current advertised floor: attach the optional file as `delegate.promptGuidelines`, re-register only when exposed metadata changes, and on modern mutable-options Pi also assign/delete **only** `event.systemPromptOptions.toolGuidelines.delegate` from the freshly registered definition. If adding a snippet, synchronize `toolSnippets.delegate` too. Do not overwrite other tools' maps or global guidelines. Preserve active tool selection; let tool-scoped gating work normally.

**C29. Alternative if the minimum is deliberately raised.** P13/P10 expose mutable named sections; the official prompt-customizer demonstrates section assignment/deletion, and custom sections render independently even with `customPrompt`, whereas default rule construction is skipped when a custom prefix is supplied. Evidence: `P13:examples/extensions/prompt-customizer.ts:39–48`; `P13:dist/core/system-prompt.js:70–121`; `P10:dist/core/extensions/runner.js:1115` onward. Recommendation: if arbitrary Markdown fidelity or support for full custom system prompts matters more than keeping 0.80.5 compatibility, prefer `sections.squire_parent_delegation` in `before_agent_start`, explicitly gated on effective delegate visibility, and omit duplicated tool guidelines. Continue re-registering the roster description. A minimum of **1.2.0 or later** additionally avoids custom-result wake gaps; using installed **1.3.0** is the clearest tested target for that design. Raising the package minimum is a product decision, not part of this report's changes.

**C30. Documentation/test seams are already present.** Tests characterize roster text at registration/session start and the child having no parent tools; the harness exposes `fire()` lifecycle dispatch but its `Tool` surface currently models selected metadata. Evidence: `S:test/tools.test.ts:26–58`; `S:test/harness.ts:60–84,205–226,341–350`; `S:README.md:206–220`. Recommendation: extend `test/tools.test.ts` and `test/harness.ts` for changed/deleted guidance and per-run roster refresh, and use a real Pi runner or SDK fixture for current-run snapshot and active-tool tests, because a Map-only fake cannot reproduce C15. Update README's session-only freshness contract, minimum/version caveats, and add a CHANGELOG entry when implemented.

**C31. Child and results delivery should not be repurposed for parent policy injection.** Child takeover is about initiating the correct first-turn prompt; parent result delivery carries actual child output, plus independently recorded result state. Evidence: `S:src/child.ts:69–86`; `S:src/results.ts:327–350`. Recommendation: no implementation changes to these files are required for optional parent guidance; add regression coverage that guidance stays out of child append files and that idle result wakes refresh on the chosen supported Pi version. Keep transport semantics separate from delegation authorization.

**C32. Prior local research is useful context, not an authority for a default policy.** The existing `docs/research/parent-waiting-guidance.md` recommends stronger waiting wording but explicitly distinguishes product-policy decisions and lack of model experiment evidence; local history includes `73ee545` (“Deliver a delegate's task as a user prompt so its first turn has the system prompt”). Evidence: `S:docs/research/parent-waiting-guidance.md:1–42`; command `git log --all --oneline --grep='prompt\|delegation\|context' -i` returned that commit. This task's optional user-authored guidance can use the API without adopting that older note's recommended autonomy/waiting policy.

## Unknowns and verification boundaries

1. **Unknown: complete package compatibility on Pi 0.80.5.** The relevant API implementation was inspected, but the full current pi-squire suite was not run against that runtime. Existing modern annotations, schema, settle/fallback, and thinking-level behavior need their own floor audit before treating the README promise as validated. This report does not claim the entire package is 0.80.5-compatible.
2. **Unknown: exact earliest release where mutating every modern structured option became supported.** P80 is inspection-only, P10 and P13 work, and the changelog places transcript sections at 0.86.0. Every intermediate release was not downloaded or executed. Do not base feature detection solely on the presence of `systemPromptOptions`.
3. **Unknown: model-behavior improvement and provider-specific cache cost.** No live model experiment or cache benchmark was run. Dynamic exposure makes text available; it does not prove reliable agent selection, obedience to user policy, or cache retention on every backend.
4. **Unknown: desired arbitrary-Markdown/custom-system-prompt contract.** The supplied proposal names `delegation.md` but does not specify whether heading/list fidelity or compatibility with a complete custom `SYSTEM.md` is required. The `promptGuidelines` choice retains the floor but is default-rules oriented; the named-section alternative handles those cases more cleanly and requires a minimum-version decision.
